## 二、Vue 组件写法强制约束

> 以下约束为**最高优先级**，所有 Vue 组件开发必须严格遵守，不得违反。

1. **禁止使用 `<script setup>` 语法糖**。Vue3 组件必须使用完整的 Vue 生命周期写法（Options API），即 `export default { data() {}, computed: {}, methods: {}, mounted() {}, beforeUnmount() {} ... }` 形式。目的是让组件结构与 Vue2 保持一致、更直观，避免语法糖带来的隐式行为。

2. **样式必须内联在组件文件内**。每个 `.vue` 文件的样式统一写在文件内的 `<style lang="scss" scoped>` 中，**即使样式超长也不要单独抽出为 `.css`/`.scss` 文件**，保持组件的样式与结构、逻辑内聚。

3. **样式必须使用 SCSS 并加 `scoped`**。所有组件样式使用 `<style lang="scss" scoped>`，通过 `scoped` 避免全局污染。

4. **通用样式统一放到 `src/style/` 目录**。全局通用样式（CSS 变量、reset、公共基础样式）统一写到 `src/style/index.scss`，并在 `main.js` 中通过 `import` 引用。组件私有样式仍内联在组件内。

5. **禁止无意义的函数拆分**。不要为了"凑行数"或"过度工程化"而把逻辑拆成碎片函数/碎片文件；拆分必须基于真实的可读性、复用或职责边界。

### Options API 组件标准结构

```vue
<template>
  <!-- 模板 -->
</template>

<script>
/**
 * 组件说明
 * @author username / useremail
 * @since yyyy-MM-dd HH:mm:ss
 */
export default {
  name: 'ComponentName',

  props: {},

  data() {
    return {}
  },

  computed: {},

  methods: {},

  mounted() {},

  beforeUnmount() {}
}
</script>

<style lang="scss" scoped>
/* 组件私有样式 */
</style>
```

## 三、项目结构与组件命名规范

### 3.1 项目目录结构规范

一个标准的 Vue 项目需要遵循清晰的目录分层，避免不同类型文件混杂，推荐采用以下结构：

| 目录 | 用途 |
|------|------|
| `src/components` | 存放全局通用公共组件，如弹窗、表单、表格等可复用基础组件 |
| `src/views` | 存放页面级业务组件，按业务模块划分子目录 |
| `src/router` | 存放路由配置文件，按业务模块拆分路由配置 |
| `src/store` | 状态管理目录，见下方「状态管理规范」的目录约定 |
| `src/utils` | 全局工具函数、请求封装、通用方法集合 |
| `src/assets` | 静态资源目录，包含图片、图标等静态文件 |
| `src/style` | 全局通用样式（SCSS 变量、reset、公共样式），统一在 `index.scss` 中管理并在 `main.js` 引用 |

这种分层方式能让新成员快速熟悉项目结构，避免多人协作时出现文件乱放的问题，大幅提升团队协作效率。

### 3.2 组件命名规范

组件命名必须遵循大驼峰规则，且名称要具备明确的语义，避免使用单个无意义的单词命名：

- **公共基础组件**统一使用通用前缀，比如 `BaseButton.vue`、`BaseTable.vue`，一眼就能识别出这是全局通用基础组件。
- **业务页面组件**使用业务相关前缀，比如 `UserProfile.vue`、`OrderList.vue`，明确标识组件所属的业务模块。

组件在模板中使用时，统一使用**短横线分隔**的形式，避免直接写大驼峰，符合 HTML 标签的书写习惯：

```html
<!-- 正确写法 -->
<base-button type="primary">提交</base-button>
<!-- 错误写法 -->
<BaseButton type="primary">提交</BaseButton>
```

## 四、Props 定义规范

### 4.1 详细定义 Props

在正式提交的代码中，Props 必须进行完整的类型定义，至少要明确指定参数类型，推荐进一步补充必填校验和自定义验证规则。这有两个核心优势：

- 作为组件的 API 文档，其他开发者打开组件就能清晰看到这个组件的使用方式，不需要反复翻看组件内部逻辑。
- 在开发环境中，Vue 会自动对传入的不符合规则的 Props 抛出警告，帮助开发者快速定位参数传递错误的问题，减少线上 bug 概率。

基础的规范写法示例：

```js
props: { status: String }
```

更完善的带校验的写法示例：

```js
props: {
  status: {
    type: String,
    required: true,
    validator: function (value) {
      return ['syncing', 'synced', 'version-conflict', 'error'].indexOf(value) !== -1
    }
  }
}
```

### 4.2 特殊类型 Props 处理

当 Props 的类型是函数时，需要单独标注类型为 `Function`，避免父组件传入普通字符串或对象导致子组件执行报错，尤其是跨组件传递回调函数的场景，类型校验能提前拦截绝大多数参数错误。

```js
props: {
  onConfirm: { type: Function, required: true }
}
```

## 五、模板编写规范

### 5.1 必须为 v-for 绑定 key

在组件上使用 `v-for` 时，必须绑定唯一的 `key` 值，这是 Vue 官方强制要求的核心规范，目的是在列表更新时维护组件内部的状态，避免出现 DOM 复用混乱的问题。即使是普通原生元素，绑定 `key` 也能保证渲染行为的可预测性，尤其是在动画切换、列表排序的场景下，能避免出现元素错位、状态丢失的问题。

```html
<!-- 不推荐，没有绑定唯一 key -->
<li v-for="todo in todos">{{ todo.text }}</li>
<!-- 正确写法 -->
<li v-for="todo in todos" :key="todo.id">{{ todo.text }}</li>
```

> **绝对不要使用数组索引作为 key 值**。当列表发生排序、增删操作时，索引会发生变化，导致 Vue 无法正确识别元素的对应关系，引发渲染异常。

### 5.2 模板表达式规范

在模板中禁止编写复杂的逻辑表达式，复杂的判断、计算逻辑统一放到 `computed` 计算属性或者 `methods` 方法中处理，保证模板的简洁可读性：

```html
<!-- 正确写法 -->
<div v-show="getLimitData(data)">...</div>
<!-- 不推荐，模板内逻辑过于复杂 -->
<div v-show="data.list.length > 5 && data.status === 'success'">...</div>
```

### 5.3 标签与特性规范

- 自定义组件的非闭合标签统一使用自闭合写法，保持代码整洁。
- 当标签的特性超过 3 个时，推荐每个特性单独占一行，避免单行代码过长难以阅读：

```html
<scroll
  ref="scrollWrap"
  class="home-scroll-warp"
  :data="homeData"
  :pullDownRefresh="true"
  :pullUpLoad="true"
  @pullingDown="pullingDownGetNewData"
  @pullingUp="pullingUpGetMore"
/>
```

- **禁止在同一个标签上同时使用 `v-if` 和 `v-for`**。`v-for` 的优先级远高于 `v-if`，会先遍历所有元素再做判断，造成不必要的性能浪费。应该先通过计算属性过滤数据，再对过滤后的结果执行 `v-for` 遍历。

## 六、状态管理规范

### 6.1 基本原则

- 项目状态统一使用 **Pinia** 进行管理，不要在组件内部随意挂载全局变量。
- 按照业务模块拆分状态模块，避免全局状态过于臃肿。
- 充分利用 Pinia 的持久化插件，处理需要跨页面保留的状态数据。

### 6.2 Store 目录约定（模块化结构）

Store 采用「入口汇总 + 业务模块分文件」的结构：

```
src/store/
├── index.js          # 入口：创建 Pinia 实例 + 通用 store + 汇总各业务模块
└── module/
    └── xxx.js        # 各业务模块 store（按模块命名）
```

- **通用 store 直接写在 `index.js`**：跨模块、与具体业务无关的共享状态（如全局加载态、用户信息等），在 `index.js` 中通过 `defineStore('common', ...)` 定义。
- **各业务模块写到 `module/` 下对应 js 文件**：如 `module/plot.js` 定义 `usePlotStore`，`module/user.js` 定义 `useUserStore`。
- **在 `index.js` 中汇总引入**各业务模块，统一导出。

### 6.3 挂载到 this.$store

在 `main.js` 中将聚合后的 store 挂载到组件实例，供 Options API 组件通过 `this.$store` 访问：

```js
import { pinia, useCommonStore, usePlotStore } from './store'

const app = createApp(App)
app.use(pinia)

const store = markRaw({
  ...useCommonStore(),   // 通用 store 挂顶层：this.$store.globalLoading
  plot: usePlotStore()   // 业务模块按模块名挂载：this.$store.plot.xxx
})
app.config.globalProperties.$store = store
```

组件内访问方式：

```js
this.$store.plot.addMessage('assistant', '你好') // 调用模块 action
this.$store.plot.deviceCount                      // 读取模块 state
this.$store.globalLoading                         // 读取通用 store state
```

## 七、代码风格与编码规范

### 7.1 代码风格

- 保持统一的代码风格（缩进使用 **2 个空格**、行尾加分号、统一换行等）。
- 遵循 Vue.js 官方风格指南和 ESLint 规范。
- 优先保障代码的可读性，避免过度压缩或炫技式写法。

### 7.2 JavaScript 规范

- 使用 ES6+ 语法（箭头函数、解构赋值、模板字符串等）。
- 优先使用 `const`，其次 `let`，避免使用 `var`。
- 函数参数不超过 3 个，超出时使用对象参数。
- 避免深层嵌套，最多 3 层。
- 模块导入：使用 ES6 `import` / `export` 语法，避免 `require`。

### 7.3 Vue 组件规范

- 组件 `props` 必须定义类型和默认值（详见「四、Props 定义规范」）。
- 单个函数长度不超过 **100 行**，超出时应考虑拆分或重构。
- 组件文件不超过 **1000 行**，超出时应拆分为多个子组件。
- 禁止使用全局变量，优先使用 Pinia 状态管理或 `props` / `emit` 传递数据。
- 使用 `computed` 处理复杂逻辑，避免在 `template` 中写复杂表达式。
- 合理使用生命周期钩子，避免在 `created` / `mounted` 中执行不必要的 DOM 操作。
- 组件销毁时清理定时器和事件监听器（`beforeUnmount`）。

## 八、命名与注释规范

### 8.1 命名规范

| 类别 | 规范 | 示例 |
|------|------|------|
| 变量名、函数名 | 小驼峰命名法（camelCase） | `userList`、`getUserList` |
| 组件名 | 大驼峰命名法（PascalCase） | `UserList.vue` |
| 文件名 | Vue 组件用大驼峰，其他文件用小驼峰或短横线分隔 | `UserList.vue`、`map-raw-device.js` |
| 常量 | 全大写加下划线 | `API_BASE_URL` |
| CSS 类名 | 短横线分隔（kebab-case） | `user-list-item` |

### 8.2 注释规范

- 所有函数、组件、关键逻辑块必须附带**清晰、准确、简洁的中文注释**。
- 核心业务逻辑、复杂工具函数必须说明**功能用途、参数含义、返回值类型**，提升代码可交接性。
- 注释应说明"为什么"而不仅是"做什么"。
- **@author 格式**：`username / useremail`（从 Git 配置获取）。
- **@since 格式**：`yyyy-MM-dd HH:mm:ss`（代码生成时的时间戳）。

组件注释示例：

```js
/**
 * 查询用户列表
 * 根据搜索条件获取用户数据并更新表格
 * @param {object} params 查询参数
 * @returns {Promise<Array>} 用户列表
 */
async getUserList(params) {
  // 实现逻辑
}
```

## 九、样式规范

### 9.1 CSS / SCSS 规范

- 使用 SCSS 预处理器，支持变量和嵌套。
- **组件样式统一内联在组件文件内**，使用 `<style lang="scss" scoped>`；即使样式超长也不单独抽出文件。
- **通用全局样式**（CSS 变量、reset、公共样式）统一放到 `src/style/index.scss`，并在 `main.js` 引用。
- 类名使用短横线分隔命名法（kebab-case）。
- 避免使用 `!important`，通过提高选择器权重解决。
- 合理使用 CSS 变量定义主题色彩。

### 9.2 Element Plus 使用规范

- 优先使用 Element Plus 组件，避免重复造轮子。
- 自定义样式时使用 `scoped` 避免全局污染（穿透子组件用 `:deep()`）。
- 主题定制通过 `src/style/` 下的全局 SCSS 变量统一管理。

### 9.3 响应式设计

- 使用 Element Plus 的栅格系统实现响应式布局。
- 移动端适配使用媒体查询。
- 图片使用相对单位，支持高分辨率屏幕。

## 十、测试要求

### 10.1 单元测试

- 为核心业务逻辑和工具函数编写**单元测试**。
- 使用 Vitest + Vue Test Utils 进行组件测试（Vue3 生态，替代 Jest）。

### 10.2 E2E 测试

- 关键业务流程编写端到端测试。
- 使用 Playwright 进行自动化测试。
- 覆盖主要用户操作路径。

### 10.3 手动测试

- 新功能开发完成后进行浏览器兼容性测试。
- 测试不同屏幕尺寸的响应式效果。
- 验证无障碍访问性（a11y）。

## 十一、代码优化与重构

### 11.1 代码优化

- 优化需**基于性能瓶颈或可维护性问题**，避免无意义的"提前优化"。
- 任何优化后必须通过**完整测试验证**，确保功能正确性。
- 在性能与可读性之间优先保障可读性，除非性能是明确瓶颈。

### 11.2 代码重构

- 重构前需明确目标（如提升可读性、消除重复、改善结构等）。
- 重构后必须通过**全部现有测试**，并补充必要新测试。
- 重构不得降低代码可读性或引入隐式复杂度。

## 十四、Git 提交规范

### 14.1 规范文档引用

完整的 Git 提交规范请参考：[`docs/GIT_COMMIT.md`](./GIT_COMMIT.md)。

### 14.2 AI 助手职责

当开发人员请求生成 Git 提交信息时，AI 助手必须：

1. **自动分析代码变更**
   - 执行 `git status` 查看变更文件
   - 执行 `git diff` 分析具体变更内容
   - 识别变更类型（新功能、修复、重构等）

2. **生成规范提交信息**
   - 格式：`[no] [type] [subject]`
   - 使用当前周任务编号（需开发人员提供）
   - 选择正确的 type 类型
   - subject 不超过 50 字符
   - body 列出所有关键变更（使用 `-` 标识）

3. **质量保证**
   - ✅ 包含任务编号
   - ✅ 正确的 type 类型
   - ✅ 简洁的 subject
   - ✅ 完整的 body
   - ✅ 格式规范

### 14.3 提交类型速查

| type | 说明 | 使用场景 |
|------|------|----------|
| `feat` | 新功能 | 新增页面、组件、业务功能 |
| `fix` | 缺陷修复 | 修复 Bug、样式问题、逻辑错误 |
| `refactor` | 代码重构 | 重构组件、优化代码结构 |
| `docs` | 文档变更 | 修改 README、注释、开发文档 |
| `style` | 样式调整 | CSS 样式修改、UI 调整 |
| `perf` | 性能优化 | 优化加载速度、减少包体积 |
| `test` | 测试代码 | 新增或修改单元测试、E2E 测试 |
| `build` | 构建调整 | Vite 配置、依赖管理、打包优化 |
| `chore` | 其他变更 | 配置文件、开发工具配置 |

### 14.4 使用示例

### 14.5 任务编号管理

- 开发人员每周提供一次任务编号。
- AI 助手自动记录到 `docs/GIT_COMMIT.md` 文档中。
- 生成提交信息时自动使用当前任务编号。

### 14.6 触发场景

AI 助手应在以下场景主动提供 Git 提交信息生成服务：

- 开发人员明确请求生成提交信息
- 完成代码开发任务后
- 开发人员询问如何提交代码时

### 14.7 自动执行 Git 操作

**重要：AI 主动询问机制**

- 生成提交信息后，AI 必须主动询问："是否需要我直接执行 git 提交并推送到远程仓库？"
- 开发人员无需主动说明，AI 会自动提示。
- 开发人员确认后，AI 自动执行：
  - `git add` 添加文件
  - `git commit` 提交到本地
  - `git push` 推送到远程仓库
  - 提供详细的执行结果反馈
